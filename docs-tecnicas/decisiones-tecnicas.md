# Decisiones técnicas — Registrapp

Registro de decisiones de diseño por defecto, según la especificación entregada el 8 de octubre de 2026 (sección 1). Estas decisiones aplican salvo que el usuario indique explícitamente lo contrario.

| # | Decisión | Valor por defecto | Motivo |
|---|---|---|---|
| D-1 | Cómo nace una institución | Una persona se registra (correo + contraseña, con confirmación de correo), y en la pantalla de onboarding crea su institución y queda como administrador | Cumple la épica 001 y evita crear cuentas sin verificar |
| D-2 | Cómo se crean los demás usuarios | El administrador los crea desde la app; el sistema genera una contraseña temporal que se muestra una sola vez, y el usuario debe cambiarla en su primer ingreso | Funciona sin depender de envío de correos |
| D-3 | Administradores por institución | Uno (índice único en la base de datos) | Así lo define el modelo de roles del proyecto |
| D-4 | Responsables y grupos | Un grupo tiene un responsable. Un responsable puede liderar varios grupos (un profesor con varios cursos) | Realismo; no cuesta más |
| D-5 | Miembros y grupos | Un miembro pertenece a un grupo | Simplicidad del modelo |
| D-6 | Vigencia del QR | El QR rota automáticamente. Cada código dura `qr_ttl_seg` (por defecto 60 s). El responsable también puede regenerarlo manualmente | Evita que alguien comparta una foto del QR con un ausente |
| D-7 | Duración de la sesión | La sesión admite registros hasta `expira_en = inicio + duracion_sesion_min` (por defecto 90 min); el responsable puede cerrarla antes | Permite registrar tardanzas reales |
| D-8 | Tolerancia de tardanza | `tolerancia_min` (por defecto 10 min): hasta ese tiempo es "puntual", después "tardanza" | Épica 003 |
| D-9 | Escaneo | Soportar ambas vías: (a) cámara nativa del celular, que abre un enlace; (b) escáner dentro de la app | Cubre el storyboard y es más robusto |
| D-10 | Zona horaria | Se guarda todo en UTC (`timestamptz`); se muestra y filtra en `America/Santiago` | Evita errores de fechas en reportes |
| D-11 | Eliminación | No se borran usuarios ni grupos con historial; se desactivan/archivan | Integridad de reportes |
| D-12 | Idioma de la interfaz | Español de Chile (es-CL), fechas `dd-MM-yyyy HH:mm` | Contexto del proyecto |

## Estado de implementación

Ninguna de estas decisiones está implementada todavía en el código (al 2026-10-09). El proyecto actual (Épica 001) solo cubre: autenticación por rol, 3 tablas base (`instituciones`, `grupos`, `usuarios`) sin los campos de D-1/D-2/D-6/D-7/D-8/D-11, y las 3 interfaces placeholder. Se implementarán en las fases correspondientes (Fase 1 en adelante) cuando el usuario confirme continuar.

## Fase 1 — decisiones tomadas al aplicar las migraciones (2026-10-09)

- **D-extra — Restricción "miembro debe tener grupo, administrador no tiene grupo"**: la sección 1.1 la marcaba como opcional ("verifica antes de aplicar"). Se verificaron los datos reales antes de aplicar: el administrador existente tenía `grupo_id = null` y los 3 miembros existentes tenían `grupo_id` asignado, así que se aplicó el constraint (`usuarios_admin_sin_grupo`, `usuarios_miembro_con_grupo`) sin conflicto.
- **Funciones de seguridad reubicadas de `public.*` a `app.*`**: las funciones de semanas 1-2 (`mi_institucion_id()`, `mi_rol()`, `mi_grupo_id()`) vivían en `public` (expuestas a la API REST). Se reemplazaron por `app.mi_institucion()`, `app.mi_rol()`, `app.mi_grupo()` y la nueva `app.soy_responsable_de(grupo_id)` (permite que un responsable lidere varios grupos, D-4). Las políticas viejas se botaron y se recrearon apuntando a las nuevas funciones.
- **Efecto secundario conocido — pendiente para Fase 2**: la pantalla de Admin → Grupos (`registrapp/src/app/features/admin/grupos/grupos.component.ts`) asigna el responsable de un grupo nuevo escribiendo directamente `usuarios.grupo_id` desde el navegador. Con las políticas nuevas, `usuarios` ya no admite ningún insert/update desde el cliente (solo Edge Functions), así que esa asignación ahora **falla en silencio** (0 filas afectadas, sin error visible). Hay que arreglarlo en la Fase 2 cuando exista la Edge Function de gestión de usuarios — mientras tanto, crear un grupo funciona, pero el campo "Responsable" que quede en la tabla `grupos.responsable_id` sí se guarda bien (esa tabla no se bloqueó); lo que no se actualiza es `usuarios.grupo_id` del responsable.

## Fase 3 — decisiones tomadas al implementar el QR (2026-10-10)

- **Transacción del `iniciar`**: supabase-js no soporta transacciones multi-tabla. En vez de una transacción SQL explícita, `sesion-asistencia` se apoya en el índice único parcial `uq_sesion_abierta_por_grupo` (grupo_id, where cerrada_en is null): si dos responsables presionan "Iniciar" a la vez, el segundo `insert` falla por violación de unicidad y la función recupera la sesión que ganó la carrera y la devuelve como "retomar", en vez de usar un lock explícito.
- **Reemplazo de `usuarios.grupo_id` por `obtenerUsuarioLlamador`**: se amplió `UsuarioLlamador` (en `_shared/supabase-admin.ts`) para incluir `grupoId`, usado por `registrar-asistencia` para el chequeo `NO_PERTENECE`. Este cambio es compatible hacia atrás con `crear-institucion`, `crear-usuario` y `actualizar-usuario`, que ya lo usaban sin ese campo.
- **D-10 (zona horaria) — bug encontrado y corregido durante la prueba end-to-end**: el mensaje `YA_REGISTRADO` (generado en el Edge Function, que corre en UTC) y la pantalla de éxito (generada en el navegador) mostraban horas distintas para el mismo instante porque ninguno de los dos fijaba `timeZone` explícito en `toLocaleTimeString`. Se corrigió fijando `timeZone: 'America/Santiago'` en ambos lados (`supabase/functions/registrar-asistencia/index.ts` y `src/app/core/utils/reloj-servidor.ts`), tal como ya indicaba D-10.
- **Verificación**: 7 pruebas Deno (`supabase/functions/_shared/qr.test.ts`) cubren token válido, firma alterada, payload alterado, vencido, dentro del margen de gracia de 5 s, y firmado con otra clave — todas pasan. Además se probó el flujo completo en el navegador con una institución real (responsable inicia sesión → QR rota con cuenta regresiva → miembro registra por `/asistir` → éxito con hora correcta → mismo token reintentado da `YA_REGISTRADO` → token vencido da `QR_EXPIRADO` → el responsable ve al miembro en "Registrados" → cerrar sesión funciona).
- **Pendiente de verificar manualmente**: el escaneo con cámara real (`/miembro/escanear`, `@zxing/browser`) no se pudo probar en este entorno por no tener una cámara física disponible; el código sigue el mismo flujo de `registrar-asistencia` ya verificado, pero conviene probarlo en un celular real antes de la demo.

## Fase 4 — decisiones tomadas al implementar el panel en tiempo real (2026-10-10)

- **Un solo canal "vivo" por pestaña**: `AsistenciaRealtimeService` es `providedIn: 'root'`, así que toda la pestaña comparte una sola suscripción Realtime activa a la vez. Esto es correcto porque el índice único `uq_sesion_abierta_por_grupo` garantiza que nunca hay más de una sesión abierta por grupo, y tanto el panel del responsable como `/admin/asistencia` solo muestran una lista en modo "vivo" por vez (las demás, si las hay, ya están cerradas y se muestran en modo "estático" sin Realtime).
- **`ListaAsistenciaComponent` reutilizado en dos pantallas**: el merge "roster de miembros + fila de asistencia" vive en un solo componente (`shared/components/lista-asistencia`) usado tanto por el panel de responsable (Fase 4.3) como por `/admin/asistencia` (Fase 4.4), evitando duplicar la lógica de conteo, orden y resaltado.
- **"Resumen final" vs "Historial reciente"**: al cerrar una sesión en el panel del responsable, la lista queda congelada en pantalla (modo solo lectura) en vez de desaparecer — eso cubre el requisito de "resumen final" de la misma sesión que se acaba de ver. El historial reciente (últimas 5 sesiones) es una sección aparte y persistente, con sus propios contadores agregados.
- **Reconexión**: `AsistenciaRealtimeService` reintenta con espera creciente (2^intentos, tope 15 s) hasta 5 veces; si sigue sin conectar, cae a consultar cada 10 s y muestra "Conexión en vivo interrumpida". También se recarga todo al volver la pestaña a primer plano (`visibilitychange`) para no perder eventos ocurridos mientras estaba oculta.
- **Verificación**: se probó insertando una fila en `asistencias` directamente por SQL (para aislar Realtime del flujo de Fase 3, ya verificado) mientras el panel del responsable estaba abierto — la lista pasó de "Ausente" a "Presente (a tiempo)" sin recargar la página. También se verificó el cierre de sesión (queda en modo solo lectura con el resumen), el historial reciente actualizándose, y `/admin/asistencia` filtrando correctamente por grupo y fecha (incluyendo que una fecha sin sesiones muestra el mensaje correcto, usando siempre America/Santiago como zona de referencia, ver `core/utils/zona-horaria.ts`).
- **Institución de prueba temporal**: para probar `/admin/asistencia` sin tocar la cuenta de administrador real del usuario, se desactivó momentáneamente "Confirm email" en Supabase Auth, se autorregistró una institución de prueba (`admin.prueba@example.com`), y se reactivó "Confirm email" al terminar. Quedó un grupo "Curso Prueba Fase 4" de prueba en esa institución nueva.

## Fase 5 — decisiones tomadas al implementar reportes (2026-10-10)

- **`v_resumen_persona`/`v_resumen_grupo` son históricos (todo el tiempo), no parametrizables por fecha**: una vista SQL no puede recibir un rango de fechas en tiempo de ejecución. Por eso la pantalla de reportes (`/admin/reportes`) y el KPI "Asistencia (30 días)" del dashboard consultan `v_asistencia_detalle` directamente con `.gte('fecha', ...).lte('fecha', ...)` y agregan en el cliente con `calcularMetricas()` (`core/utils/metricas-asistencia.ts`), usando exactamente las mismas fórmulas que las vistas SQL. La tabla de grupos del dashboard sí usa `v_resumen_grupo` tal cual (histórico completo), tal como pide la Fase 5.4.
- **Resumen por grupo/persona y exportación usan la misma función**: tanto las pestañas "Resumen" de `/admin/reportes` como la exportación llaman a `reportesService.obtenerTodo()` (pagina en bloques de 1000 vía `.range()`) y agregan con `agruparPorGrupo`/`agruparPorPersona`. Esto garantiza que lo exportado coincida exactamente con lo que se ve en pantalla (mismo filtro, misma consulta, mismo cálculo), sin duplicar lógica.
- **SheetJS instalado desde el tgz del CDN oficial** (`https://cdn.sheetjs.com/xlsx-latest/xlsx-latest.tgz`), no desde npm, como pide la especificación (el paquete `xlsx` de npm está desactualizado). Queda fijado en `package.json` a esa URL exacta.
- **pdfmake 0.3.x**: el patrón de inicialización cambió respecto a versiones anteriores — ya no es `pdfMake.vfs = pdfFonts.pdfMake.vfs`, sino `pdfMake.vfs = pdfFonts` directo (`vfs_fonts.js` ahora exporta el mapa de fuentes tal cual).
- **Bug encontrado y corregido en `/miembro/historial`**: al formatear `fecha` (una fecha pura `yyyy-MM-dd` que ya viene en America/Santiago desde la vista) con `new Date(fecha).toLocaleDateString(..., { timeZone: 'America/Santiago' })`, un string sin hora se interpreta como medianoche UTC, y convertirlo de nuevo a America/Santiago le resta el día (ej. una sesión del 10-10 aparecía como 09-10). Se corrigió formateando el string directamente (`split('-')`), igual que ya se hacía en `exportacion.service.ts`. El pipe `date` de Angular (usado en `/admin/reportes`) no tiene este problema porque internamente trata las fechas sin hora como componentes locales, no como un instante UTC.
- **Verificación manual obligatoria (hecha)**: se crearon 3 sesiones reales para un grupo de prueba con asistencias conocidas (1 puntual, 1 tardanza, 1 ausente) y se comprobó a mano: % asistencia = 2/3 = 66.7%, % tardanza = 1/3 = 33.3% — coincide exactamente en "Resumen por curso", "Resumen por persona", "Detalle", el dashboard (tarjeta y tabla) y `/miembro/historial`. La exportación a Excel y PDF corrió sin errores en consola (no se pudo abrir el archivo descargado dentro de este entorno de pruebas para inspeccionar el contenido binario; recomendado confirmarlo manualmente).
